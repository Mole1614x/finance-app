# PR 6: ARTH-only simulated peer payments
Initialize accounts on two fictional users. Receive shows a unique ARTH demo identifier based on the checking account UUID and a real QR matrix containing that identifier (not a UPI URI). The sender enters that identifier, enters an INR amount, reviews and explicitly confirms. The backend transfers integer paise atomically between checking accounts. Receipt reference is visible to both participants. Real payments remain disabled.

Endpoints: GET /api/v1/payments/receive, POST /resolve, POST /send (Idempotency-Key required), GET /{payment_id}, all under /api/v1/payments. Sender and recipient owners are locked in deterministic order. Existing ledger journal kind 'internal' means internal to the ARTH network; a separate demo_payments row identifies peer transfers without modifying existing ledger schema constraints. No actual bank account, phone, UPI identifier or external payment provider is accepted. No money is redeemable.

The mobile QR route accepts already-decoded text; camera access and on-device QR decoding are not implemented. Idempotency key is retained in memory on retry; app restart or explicit discard loses this reference, and a new payment could repeat an earlier unknown-outcome transfer. Durable pending payment recovery is future work. Existing chart remains illustrative. Full history and transaction management are PR 7. SQLite tests cover replay, access, concurrency and reconciliation; PostgreSQL and device runtime not verified. Original Figma assets and exact visual parity remain outstanding. Never deploy this demonstration publicly.
