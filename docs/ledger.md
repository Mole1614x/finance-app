# PR 5 — Simulated accounts and paired ledger
All amounts are integer INR paise. New users have zero ledger balance until they explicitly initialize accounts. Initialization creates checking, savings and a hidden per-user funding counter-account; a single opening journal pair grants INR 8,500 of simulated funds. Repeated initialization does not mint funds. No bank credentials are collected. Nothing is redeemable.

Journal rows represent equal and opposite debit/credit postings in a wallet-liability convention (debit decreases a balance, credit increases it). Each row contains both account IDs and one positive amount, structurally conserving value. Account balances are cached and updated in the same transaction. The funding counter-account may be negative; user-facing accounts may not. Only authenticated users can initialize or move funds between their own checking and savings. Per-owner locking is obtained via an update on the user row before reading ledger state. Idempotency is owner-scoped and mismatched replays are rejected. Failed moves roll back. No update/delete journal API exists, but database-level immutable journal enforcement and migrations are future work.

Endpoints: GET /api/v1/accounts, POST /api/v1/accounts/initialize, POST /api/v1/accounts/move with Idempotency-Key header and source/destination kinds and integer amount_minor. Authenticated dashboard now reports actual simulated ledger balances; the chart is still illustrative. Mobile account screen can initialize and refresh accounts; internal moves currently via API only. Peer-to-peer transfers and QR are PR 6. Tests use SQLite; PostgreSQL runtime/concurrency checks, physical devices and exact Figma assets remain outstanding. Do not deploy this demo publicly.
